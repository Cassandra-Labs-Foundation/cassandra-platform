# Backend and control architecture

[Open the interactive architecture explorer](https://cassandra-labs-foundation.github.io/cassandra-platform/architecture/#/overview).

The explorer maps the whole system and lets you drill into it. Views are drawn as flow diagrams — ports, labeled arrows and branches say who calls whom and what flows where (the overview draws request → console → Core API → Postgres / Blnk and back; a module draws callers → operations → emitted events → the controls they serve; a control draws triggering events → required behaviour → produced events; the pipeline draws its steps in run order). Open a block to reveal its contents; use the ancestor breadcrumbs to return to the enclosing view. It has two layers, and the page labels which one you are looking at.

**The inventory covers everything, and every container drills down.** Every deployable (the Core API, the aggregator, the Blnk webhook and reconciler, the control drill, Postgres, the Blnk ledger, the staff console), every API module grouped by domain, every operation in the spec, and every policy and control in the catalogue. From the Core API you reach a domain, then a module (its operations, the event codes it emits, the controls those events serve, the gate controls the crosswalk says it implements, what it imports and what imports it), then one operation (its route, audience, tier, actors, handler and the live flows that call its path). From Policies & controls you reach a policy, then a control (its triggering and produced events, the modules that emit them, its hermetic and live status, its scope verdict and reachability), then one event code (its emit sites, line by line, and every control it serves). Each of the other edge functions opens into its files, and a file into its exported symbols with line links. Postgres opens into every table (replayed from the migrations; a table shows its columns and the modules that reference it) and every declared state machine. The staff console opens into its pages, and a page into the operations its source names. The specification pipeline opens into the actual steps of `scripts/rebuild_artifacts.sh`, each linking to its script.

**The traced path covers one control in depth.** BSA-06 is followed by hand from the payment gate through alert triage to a recorded SAR decision, down to the checks and writes behind each decision. Open it from the control page for BSA-06, or from the Core API's manually traced slices, which also hold the request path and the payment gate's call sites.

## What each layer establishes

The inventory is `system.json`, generated by `scripts/gen_architecture.py` from `core/core-api.yaml`, the `api/` module sources, the other edge functions' sources, `crosswalk-emitted-events.json`, `controls.json`, `control-scope.json`, `control-tests.json`, `control-tests-live.json`, `crosswalk.json`, the live flows under `core/verifier/flows/`, the migrations under `core/supabase/migrations/`, the console pages under `ui/src/pages/` and the rebuild order in `scripts/rebuild_artifacts.sh`. It is complete by construction, because it enumerates those sources rather than selecting from them. It states declared facts and static references only. "Module X emits event Y" comes from the emitted-events inventory. "Flow Z calls this path" is a path match in the flow's source, not a test run. Gate-control claims are the crosswalk's reviewed, hand-authored assertions, and are labelled as such. The domain grouping in `DOMAINS` is the one hand-authored input. A module missing from it shows as "Unclassified", and `check_architecture.py` fails.

The traced path is `model.json`, a manually traced source snapshot. Its footer identifies the inspected revision. Policy intent, implementation behavior, supporting source and test definitions, and review boundaries stay separate. A test link is not a passing test run. An event name is not proof of an external action. The slice covers one path within BSA-06. Other detectors, external filing, Board reporting, timer sweeps and full retention enforcement are outside it.

The payment gate is implemented in `core/supabase/functions/api/transfers.ts` and contains explicit checks. The extracted control catalogue and crosswalk are documentation and evidence inputs. They should not be described as a runtime rules interpreter. CDA has its own funding gate. Coverage must be established from actual call sites and early returns, not from an "all rails" label.

## Maintain the model

- `system.json` is generated; never edit it. `scripts/rebuild_artifacts.sh` regenerates it. The Pages workflow also regenerates it from the pushed tree before publishing, so the live site always reflects `main`.
- `model.json` contains the traced slice, its implementation mechanics and reviewed source fingerprints. Its `control` field names the catalogue control the slice belongs to.
- `explorer.mjs` renders the hand-written views and the traced slice; `inventory.mjs` renders the generated views.
- `navigation.mjs` defines stable routes (`#/module/<name>`, `#/op/<METHOD path>`, `#/control/<policy:ID>`, …), ancestor state and legacy-route aliases.
- `explorer.css` defines the responsive interface. `index.html` is the published entry point and loads only local assets.

Use the repository skill at `.skills/visual-control-architecture/SKILL.md` to revise or extend the traced model. Re-read the affected policy, handlers, helpers and tests before changing claims. Update the inspected revision and fingerprints only after reviewing the sources, never as an automatic way to clear a check. Fingerprints detect changed inputs; they do not validate the interpretation or discover newly relevant code.

Validate with:

```sh
python3 scripts/gen_architecture.py --check
python3 scripts/check_architecture.py
node --test docs/architecture/navigation.test.mjs
python3 scripts/check_doc_claims.py
```

The end-to-end test walks the explorer the way a reviewer does, in a real browser. It drills to an operation, to a control's traced decision, to a function file, a table, a state machine, a console page, an event's emit site and a pipeline step, and climbs back through the breadcrumbs. It also checks that every API module, operation, policy, control, function file and console page is reachable, against totals read from `STATE.md` and the source directories rather than from `system.json`:

```sh
cd docs/architecture/e2e && npm ci && npx playwright install chromium
npm test                                                                  # serves docs/ locally
BASE_URL=https://cassandra-labs-foundation.github.io/cassandra-platform npm test  # the published site
```

To inspect the explorer by hand, serve the repository's `docs/` directory with any local HTTP server and open `/architecture/`. Opening it straight from the filesystem doesn't work, because the page loads its models over HTTP. Old overview, containers, components and walkthroughs hashes remain usable.

Current repository-wide counts remain in [STATE.md](../../STATE.md). The explorer is a human review surface, not operational monitoring or an automated compliance verdict.
