# Backend and control architecture

[Open the interactive architecture explorer](https://cassandra-labs-foundation.github.io/cassandra-platform/architecture/#/overview).

The explorer maps the whole system and lets you drill into it. Every view is a flow diagram: boxes joined by drawn, labeled arrows that say who calls, imports, stores, emits or derives what. The overview is a container diagram (people → staff console and Core API → supporting functions → shared code → Postgres, Blnk and analytics, with the design-time policies, pipeline and CI below). The Core API is a component diagram (callers by audience → router → authentication → domains → shared modules → stores). A module, operation, control, event, table, file, page and pipeline step each draw their own neighbourhood, and the traced BSA-06 processes are flowcharts with labeled branches. Open a box to see what is inside it; use the ancestor breadcrumbs to return to the enclosing view. **Engineering detail** adds each box's identifiers (file and line, handler, operationId, uid, column types) and an implementation contract to the inspector, on every view. It has two layers, and the page labels which one you are looking at.

Arrows are routed through the gaps between boxes, never through one. Solid arrows are static references found in source; dashed arrows are tests, evidence, schedules and runtime callbacks a header or workflow states; dotted arrows are reviewed claims, declared order or design-time derivations. One arrow to a group frame stands for the same arrow to every box in it, and three or more arrows between the same two groups are drawn as one; a domain's arrow to a store says how many of its modules make that reference. Arrows into one box merge at a single entry point. In a busy diagram, arrows that skip a row stay out of the resting picture unless a box would otherwise look unconnected; pointing at or focusing a box highlights every arrow that touches it, hidden ones included, and a line under the diagram says how many are hidden. Every arrow, collapsed or hidden, is still listed for screen readers. Where a diagram has to cap a long list, the complete listing follows it.

**The inventory covers everything, and every container drills down.** Every deployable (the Core API, the aggregator, the Blnk webhook and reconciler, the control drill, Postgres, the Blnk ledger, the staff console), every API module grouped by domain, every operation in the spec, and every policy and control in the catalogue. From the Core API you reach a domain, then a module (its operations, the event codes it emits, the controls those events serve, the gate controls the crosswalk says it implements, what it imports and what imports it), then one operation (its route, audience, tier, actors, handler and the live flows that call its path). From Policies & controls you reach a policy, then a control (its triggering and produced events, the modules that emit them, its hermetic and live status, its scope verdict and reachability), then one event code (its emit sites, line by line, and every control it serves). Each of the other edge functions, the shared function code and the analytics jobs opens into its files, laid out by import depth, and a file into its exported symbols with line links. Postgres opens into its schemas, every table (replayed from the migrations; a table shows its columns, its foreign keys in both directions and the code that references it) and every declared state machine. The staff console opens into its pages, and a page into the operations its source names. The specification pipeline opens into the actual steps of `scripts/rebuild_artifacts.sh`, each linking to its script.

**The traced path covers one control in depth.** BSA-06 is followed by hand from the payment gate through alert triage to a recorded SAR decision, down to the checks and writes behind each decision. Open it from the control page for BSA-06, or from the Core API's manually traced slices, which also hold the request path and the payment gate's call sites.

## What each layer establishes

The inventory is `system.json`, generated by `scripts/gen_architecture.py` from `core/core-api.yaml`, the `api/` module sources, the other edge functions' sources, `crosswalk-emitted-events.json`, `controls.json`, `control-scope.json`, `control-tests.json`, `control-tests-live.json`, `crosswalk.json`, the live flows under `core/verifier/flows/`, the migrations under `core/supabase/migrations/`, the console pages under `ui/src/pages/`, the scripts under `analytics/`, the workflows under `.github/workflows/` and the rebuild order in `scripts/rebuild_artifacts.sh`. The container-to-container arrows come from the same sources: cross-function imports, schema-resolved table references (`schema("core").from("account")`), the shared Blnk client and the scripts each workflow runs. It is complete by construction, because it enumerates those sources rather than selecting from them. It states declared facts and static references only. "Module X emits event Y" comes from the emitted-events inventory. "Flow Z calls this path" is a path match in the flow's source, not a test run. Gate-control claims are the crosswalk's reviewed, hand-authored assertions, and are labelled as such. The domain grouping in `DOMAINS` is the one hand-authored input. A module missing from it shows as "Unclassified", and `check_architecture.py` fails.

The traced path is `model.json`, a manually traced source snapshot. Its footer identifies the inspected revision. Policy intent, implementation behavior, supporting source and test definitions, and review boundaries stay separate. A test link is not a passing test run. An event name is not proof of an external action. The slice covers one path within BSA-06. Other detectors, external filing, Board reporting, timer sweeps and full retention enforcement are outside it.

The payment gate is implemented in `core/supabase/functions/api/transfers.ts` and contains explicit checks. The extracted control catalogue and crosswalk are documentation and evidence inputs. They should not be described as a runtime rules interpreter. CDA has its own funding gate. Coverage must be established from actual call sites and early returns, not from an "all rails" label.

## Maintain the model

- `system.json` is generated; never edit it. `scripts/rebuild_artifacts.sh` regenerates it. The Pages workflow also regenerates it from the pushed tree before publishing, so the live site always reflects `main`.
- `model.json` contains the traced slice, its implementation mechanics and reviewed source fingerprints. Its `control` field names the catalogue control the slice belongs to.
- `diagram.mjs` lays out and draws every diagram; `explorer.mjs` defines the hand-written views and the traced slice; `inventory.mjs` defines the generated views.
- `navigation.mjs` defines stable routes (`#/module/<name>`, `#/op/<METHOD path>`, `#/control/<policy:ID>`, …), ancestor state and legacy-route aliases.
- `explorer.css` defines the responsive interface. `index.html` is the published entry point and loads only local assets.

Use the repository skill at `.skills/visual-control-architecture/SKILL.md` to revise or extend the traced model. Re-read the affected policy, handlers, helpers and tests before changing claims. Update the inspected revision and fingerprints only after reviewing the sources, never as an automatic way to clear a check. Fingerprints detect changed inputs; they do not validate the interpretation or discover newly relevant code.

Validate with:

```sh
python3 scripts/gen_architecture.py --check
python3 scripts/check_architecture.py
node --test docs/architecture/navigation.test.mjs
python3 scripts/check_doc_claims.py
```

The end-to-end test walks the explorer the way a reviewer does, in a real browser. It drills to an operation, to a control's traced decision, to a function file, a table, a state machine, a console page, an event's emit site and a pipeline step, and climbs back through the breadcrumbs. On every kind of view it checks that the map is a drawn diagram (boxes, labeled edges, no edge to a missing box), that no edge passes through a box it does not connect, that no box looks unconnected at rest and hidden edges appear on hover, and that Engineering detail changes what is shown. It also checks that every API module, operation, policy, control, function file and console page is reachable, against totals read from `STATE.md` and the source directories rather than from `system.json`:

```sh
cd docs/architecture/e2e && npm ci && npx playwright install chromium
npm test                                                                  # serves docs/ locally
BASE_URL=https://cassandra-labs-foundation.github.io/cassandra-platform npm test  # the published site
```

To inspect the explorer by hand, serve the repository's `docs/` directory with any local HTTP server and open `/architecture/`. Opening it straight from the filesystem doesn't work, because the page loads its models over HTTP. Old overview, containers, components and walkthroughs hashes remain usable.

Current repository-wide counts remain in [STATE.md](../../STATE.md). The explorer is a human review surface, not operational monitoring or an automated compliance verdict.
